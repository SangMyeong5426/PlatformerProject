# 나중에 확인할 것

**결함 목록이 아니다.** 지금 잘못 돌고 있는 것은 고치거나 work log 에 적는다. 여기 있는 것은
**지금은 판단할 근거가 없거나 확인할 수단이 없어서 미뤄 둔 것**이다.

미뤘다는 사실을 어딘가에 적어 두지 않으면 조건이 갖춰진 뒤에도 아무도 다시 오지 않는다.

## 규칙

- 항목을 지울 때는 **무엇을 확인했고 결론이 무엇이었는지**를 관련 문서에 먼저 남기고 지운다.
  그냥 지우면 확인한 것인지 잊은 것인지 구분되지 않는다.
- **조건이 갖춰졌는데 아직 안 한 것**과 **조건이 아직인 것**을 섞지 않는다. `언제` 칸이 그
  구분이다.
- 근거가 ADR 이나 work log 에 있으면 그것을 가리키고 여기에 다시 적지 않는다.

## 9 · 대사를 Unity Localization 문자열 테이블로 옮긴다

대사가 `GenerateData()`/`GenerateDataENG()` 안에 하드코딩돼 있다. 언어를 추가하려면 코드를
고쳐야 하고, 대사 한 줄을 바꾸는 데도 컴파일이 필요하다.

프로젝트는 **이미 Unity Localization 을 쓴다.** `Assets/Language/` 에 English (en) 와
Korean (South Korea) (ko-KR) 로케일과 문자열 테이블이 있고, UI 일부가 그것을 읽는다.
대화만 따로 놀고 있다.

C단계에서 하지 않은 이유: **이건 리팩토링이 아니라 데이터 이관이다.** 대사가 사는 자리가
코드에서 에셋으로 바뀌고, 테이블 편집은 에디터에서 해야 한다. 공통 골격 정리와 같은
커밋에 넣으면 무엇이 구조 변경이고 무엇이 데이터 이동인지 구분되지 않는다.

옮길 때 정할 것: 키 규칙(`talk.tutorial.1` 같은), 빈 문자열로 끝나는 마지막 항목을
어떻게 다룰지(지금은 `Add(n, "")` 가 종료 표시처럼 쓰인다).

## 10 · CP949 파일이 아직 남아 있다

사용자 작업 영역에 CP949 로 저장된 `.cs` 가 남아 있다. 편집 대상이 될 때마다 UTF-8(BOM)
으로 정규화하고 **정규화를 내용 변경과 별도 커밋으로 분리**한다는 원칙을 지키고 있다.

한꺼번에 전부 변환하지 않는 이유는 거대한 diff 하나가 생기고 그 안에 실수가 섞여도 알 수
없기 때문이다. 검증 도구(`scripts/boss-pattern-diff`)는 양쪽 인코딩을 모두 읽으므로 남아
있어도 검증이 막히지는 않는다.

## 1 · 검증 도구가 저장소에 없다 — 완료 (2026-08-31)

`scripts/boss-pattern-diff` 와 `scripts/baseline/boss-patterns.txt` 로 넣었다. 보스 5종
패턴 21개의 실행 시퀀스를 뽑아 리팩토링 직전(`2f023e52`)과 대조한다.

**기준은 애초에 사라진 적이 없었다.** 리팩토링 전 소스가 `2f023e52` 에 그대로 있어서 언제든
다시 뽑을 수 있었다. 잃었던 것은 비교 대상이 아니라 **비교하는 도구**였다.

범위를 `2f023e52`..`626a80f0` 구간 보스 패턴으로 한정했다. **앞으로의 리팩토링에 쓸 범용
도구로 만들지 않았다** — C단계(Talk 통합)는 대사 순서와 진행도 분기를 봐야 해서 필요한
검증이 아예 다르다. 지금 범용 도구를 지으면 무엇이 필요한지 모르는 채로 짓는 것이다.
C단계에서 만든 도구가 쌓이면 그때 공통점이 보인다.

다시 확인한 것: 커밋이 적은 "20/20" 과 이 도구의 21개가 다르다. 어느 쪽이 맞는지 확정하지
못했고 그 사실을 `scripts/README.md` 에 남겼다.

## 5 · 바람 보스 탄막 60발

`BurstOffsets` 4회 x 15발 = 60발이 나가야 한다. 정적 대조로는 연산 69개 완전 일치를
확인했으나 런타임에서 세지 못했다.

**원인을 잘못 적어 뒀던 것을 2026-09-01 에 정정한다.**

원래 여기에 "Unity 창이 비활성이면 게임 루프가 진행되지 않는다"고만 적어 뒀다. 증상은
맞지만 **원인을 창 포커스로 오해한 것**이다. 실제 원인은 프로젝트 설정 한 줄이었다.

```
ProjectSettings/ProjectSettings.asset:79   runInBackground: 0
```

Unity 의 기본값이 `0` 이라 창이 비활성이면 플레이어 루프가 멈춘다. 창 포커스는 그 설정이
드러나는 조건이지 원인이 아니었다. 값을 `1` 로 바꿨다([ADR-0005](adr/0005-batchmode-playmode-tests.md)).

**증상을 원인으로 적어 두면 조건이 갖춰져도 다시 오지 않는다.** "창을 봐야 한다"는 사람이
지켜야 하는 제약처럼 읽히지만, "설정이 꺼져 있다"는 고칠 수 있는 것이다. 여기 적힌 다른
항목도 같은 오류가 있을 수 있다.

세는 것은 `scripts/playmode-test` 가 대신한다. 배치모드는 창이 없어 이 설정과 무관하다.

## 6 · `Earth_Bullet` 이 다른 보스의 데미지 값을 읽는다 — 완료 (2026-08-31)

**오타로 결론 내고 자기 값을 읽도록 고쳤다.** 근거와 판단 과정은
[work log](work-log/2026-08-31-talk-and-bugfixes.md) 에 있다. 아래는 당시의 기록이다.

`Basic_Boss` 는 데미지 값을 종류별로 갖고 있다.

```csharp
public int EarthBullet_Damage = 1;
public int IceWave_Damage = 1;
```

`Earth_Bullet.cs:11` 의 `EarthBullet_Damage` 는 **`Basic_Boss` 를 가리키는 참조 필드**이고,
41~42행에서 그 보스의 `IceWave_Damage` 를 읽는다.

```csharp
public Basic_Boss EarthBullet_Damage;          // 11행 — 보스 참조
player_Hp.TakeDamage(EarthBullet_Damage.IceWave_Damage);   // 42행
```

같은 대지 보스 계열인 `EarthGrow.cs:31` 은 `Earth_Damage.EarthBullet_Damage` 로 **자기
데미지를 읽는다.** `Earth_Bullet` 만 다르다.

**현재는 아무 차이가 없다.** 프리팹 5개를 전부 확인했는데 두 값이 모두 `1` 이다. 값을 다르게
조정하는 순간 드러나는 잠복 결함이다.

고치면 대지 보스 탄환의 데미지 계산 근거가 바뀐다. **원래 의도가 무엇이었는지 확인이
필요하다.** 필드 이름이 헷갈리게 지어져 있어(참조 필드에 데미지 이름을 붙였다) 오타일
가능성이 높지만 단정할 수 없다.

## 7 · 바람 보스 패턴 2·3 이 둘 다 `SpawnTornado` — 완료 (2026-08-31)

**빠뜨린 패턴으로 결론 내고 `case 3` 을 `SpawnBullet` 로 고쳤다.** 처음엔 "판단 보류"로
정했다가, 사용자가 원래 구성을 기억해 내서 다시 확인했고 그 기억이 맞았다. 아래는
당시의 기록이다.

원래 `switch` 문의 `case 2` 와 `case 3` 이 같은 함수를 불렀다. 2단계에서 **동작 보존을 위해
`BuildPatterns()` 배열에 두 번 넣어** 확률을 그대로 유지하고 있다.

두 가지로 읽힌다.

- **토네이도가 나올 확률을 2배로 준 의도** — 그렇다면 지금이 맞고 주석만 달면 된다
- **다른 패턴을 넣으려던 자리** — 그렇다면 패턴이 하나 비어 있는 것이다

바람 보스는 패턴이 실질 3종(텔레포트·돌진·토네이도)이라 다른 보스보다 단조롭다. 어느 쪽인지
**확인이 필요하다.**
