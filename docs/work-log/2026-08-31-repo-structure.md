## PR 을 안 쓰기로 하면서 생긴 구멍

본보기로 삼은 [`skalounge`](https://github.com/simonjiho/skalounge) 를 다시 읽었다. 규칙의
절반이 **CI 가 강제하는 장치**로 되어 있었다 — `AGENTS.md`/`CLAUDE.md` 를 diff 로 비교하는
검사, ADR 번호 충돌 검사, `main` push 감사. 이 저장소는 1인 · CI 없음이라 그대로 옮기면 빈
껍데기가 된다.

문제는 그게 아니었다. **skalounge 의 가장 중요한 규칙이 PR 본문에 얹혀 있다.**

> 되돌린 접근 / 발견해 고친 결함 / 검증하지 못한 항목을 반드시 PR 본문에 남긴다

Squash merge 만 쓰므로 PR 본문이 `main` 에 남는 유일한 기록이기 때문이다. 그런데 이 저장소는
**혼자 작업하니 PR 을 쓰지 않기로 했다.** 그 순간 그 기록의 자리가 통째로 없어진다.

커밋 메시지는 대신하지 못한다. 커밋은 "이 변경"만 설명하고, **"해봤다가 되돌렸다"는 어느
커밋에도 속하지 않아 적을 자리가 없다.** 그래서 `docs/work-log/` 를 만들었다. 이 문서가
그 자리다.

## 판정 방법이 틀렸다 — 부모 클래스를 죽은 것으로 셌다

`X/` 와 `test/` 폴더의 16개를 정리하려고 **씬·프리팹에서 GUID 참조가 0건인 것**을 죽은
코드로 셌다. 7개가 나왔다.

그중 `Boss.cs` 가 **살아 있었다.** 씬은 자식 클래스(`Final_Stage_Boss`)를 참조하고 부모는
직접 참조하지 않는다. **이 방법은 부모 클래스를 항상 죽은 것으로 판정한다.**

지웠으면 `FinalBoss.prefab` 이 깨졌다. ADR 을 쓰고 이동 대상을 가르는 과정에서 발견했다 —
**계획서를 쓰지 않고 바로 옮겼으면 놓쳤을 것이다.**

고친 판정: **씬·프리팹의 GUID 참조**와 **다른 `.cs` 의 타입 참조**를 함께 본다. 둘 다
0건이어야 죽은 것이다.

타입 참조를 셀 때도 함정이 하나 더 있었다. **이름이 같다고 참조가 아니다.**

다시 세니 6개였고, 이후 `Assets/` 루트의 `TouchObj`·`Buttonclick` 과 본문이 전부 주석

## 이동은 Unity 를 닫고 했다

`.cs` 를 옮길 때 `.meta` 를 함께 옮겨야 한다. 씬은 파일 경로가 아니라 `.meta` 안의 GUID 로
스크립트를 참조하므로, 둘이 같이 움직이면 씬은 아무것도 모른다.

**에디터가 켜져 있으면 안 된다.** `.cs` 는 도착했는데 `.meta` 가 아직인 순간을
`AssetDatabase` 가 보면 **새 GUID 를 발급해 버린다.** 그 스크립트를 쓰는 모든 컴포넌트가
`Missing` 이 된다.

처음에 "닫아 달라"고만 말했더니 **닫고 바로 다시 켜셨다.** 내 설명이 부족했다 — 이동하는
*동안* 닫혀 있어야 한다는 말을 하지 않았다. `Temp/UnityLockfile` 로 확인하고 다시 요청했다.

**검증:** 파일마다 이동 전후 GUID 를 대조했다. 134개 전부 일치, 불일치 0. git 이 전부
rename 으로 인식해 내용 변경이 0줄이다.

**이동 커밋 3개가 `.unity`·`.prefab` 을 0개 건드렸다.** 그래서 인스펙터 값이 그대로인 것은
따로 확인할 필요가 없다 — 직렬화된 값은 씬 파일 안에 있고 파일을 옮기는 것만으로는 손댈 수
없다. 처음에 인스펙터를 확인해 달라고 요청했는데 불필요한 요청이었다.

## 검증 도구를 다시 만들었다

어제 커밋들이 "패턴 시퀀스 20/20 일치"라고 적었는데 그것을 확인한 도구가 세션 스크래치패드에만
있었고 사라졌다. **주장은 남고 재현할 수단이 없는 상태**였다.

먼저 확인한 것: **기준은 애초에 사라진 적이 없다.** 리팩토링 전 소스가 `2f023e52` 에 그대로
있다. 잃었던 것은 비교 대상이 아니라 **비교하는 도구**다.

`scripts/boss-pattern-diff` 로 다시 만들어 커밋했다. 보스 5종 패턴 21개, 951줄이
`2f023e52` 와 완전히 일치한다.

**범위를 한정했다.** `2f023e52`..`626a80f0` 구간 보스 패턴 전용이다. 앞으로의 리팩토링에 쓸
범용 도구로 만들지 않았다 — C단계는 대사 순서와 진행도 분기를 봐야 해서 필요한 검증이 아예
다르다. 무엇이 필요한지 모르는 채로 범용 도구를 지으면 둘 다 어중간해진다.

### heredoc 이 또 백슬래시를 먹었다

스크립트를 셸 heredoc 으로 만들려다 두 번 깨졌다. **어제 work log 에 적어 둔 것과 같은
부류다.** 이번엔 진단이 빨랐다 — 파일 도구로 직접 쓰는 것으로 바꿨다.

기록해 둔 것이 실제로 도움이 됐다.

### 도구가 처음에 죽었다 — `Boss_mode.cs` 가 CP949

`Boss_mode` 를 대조에 넣자 디코딩에서 터졌다. 아직 정규화되지 않은 CP949 파일이었다.

**인코딩 때문에 검증이 막히면 안 된다.** UTF-8 을 먼저 시도하고 CP949 로 물러나게 했다.
파일 자체는 이번에 고치지 않았다 — 편집 대상이 될 때 정규화한다는 원칙을 유지했다.

### 수치가 커밋 메시지와 다르다

도구는 패턴을 **21개**로 세는데 어제 커밋은 **20/20** 이라고 적었다. 당시 도구가 없어 20이
무엇을 빼고 센 값인지 확인할 수 없다.

**어느 쪽이 맞는지 확정하지 못한 채로 남겼다.** 21개 전부가 일치하므로 검증 결론은 달라지지
않지만, 수치가 다르다는 사실을 지우지 않는다. `scripts/README.md` 에 적었다.
