## 무엇을 했는가

보스 골격이 정리된 뒤, 같은 방식으로 **나머지 영역의 복붙과 매 프레임 낭비**를 걷어냈다.

## 이날 가장 값이 나온 것 — `StageId`

보스 사망 처리에서 "어느 스테이지를 클리어했는가"를 표현할 방법이 필요해 enum 하나를 만들었다.

```csharp
public enum StageId { First = 0, Second = 1, Third = 2, Fourth = 3 }
```

만들 때는 보스 4종만 쓸 생각이었는데, **결국 세 군데에서 재사용됐다.**

| 어디 | 무엇이 사라졌나 |
| --- | --- |
| `BoolManager` | `static bool` 4개 → `bool[]` + API 3개 |
| `EnemyCountManager` | 스테이지 4개 블록 복붙 → 배열 인덱스 |
| `BossClearPortal` | 포탈 클래스 4개 → 1개 (다음 단계에서) |

**값을 명시적으로 적어 둔 이유**(`First = 0` …)는 `BoolManager` 가 배열 인덱스로 쓰기
때문이다. enum 순서를 바꾸면 저장된 플래그가 어긋난다. 주석으로 남겼다.

## 매 프레임 비용 — 두 종류를 다르게 처리했다

**빈 `Update()`/`Start()` 30개 제거 (27개 파일, 148줄 삭제).** 빈 `Update()` 는 비용이 0이
아니다. Unity 는 `Update` 를 가진 컴포넌트마다 네이티브에서 매 프레임 메시지를 디스패치하므로,
**메서드 자체가 없어야** 그 호출 목록에서 빠진다.

안전성을 두 가지로 확인했다 — 대상 27개 클래스를 상속하는 클래스가 없어 `base.Update()` 를
부르는 곳이 없고, 본문 판정 시 `//` 주석만 걷어내고 `/* */` 블록은 남겨 **주석 처리된 코드가
들어 있는 메서드는 제외**했다.

**씬 전환 판정을 폴링에서 이벤트로.** `Destroy` 가 매 프레임 씬 이름을 문자열 비교하고
`DontDestroyOnLoad` 를 다시 호출하고 있었다. `activeSceneChanged` 구독으로 바꿔 `Update()`
자체를 없앴다.

여기서 두 가지를 판단해야 했다.

- **구독을 `OnEnable`/`OnDisable` 이 아니라 `Awake`/`OnDestroy` 에 뒀다.** 관례는 전자지만,
  **비활성 상태에서 씬이 바뀌면 그 전환을 놓친다.** 이 컴포넌트는 씬을 넘어 살아남는 것이
  목적이라 놓치면 안 된다
- **`Start()` 에서 현재 씬을 한 번 판정한다.** `activeSceneChanged` 는 이미 열려 있던 씬에
  대해서는 발생하지 않아, 이게 없으면 최초 판정이 통째로 누락된다

## 합치지 않기로 한 것 — `DestroyPL`

`Destroy` 와 `DestroyPL` 은 씬 이름 목록만 다른 같은 코드였다. **한 클래스로 합치는 게
깔끔하지만 그렇게 하지 않았다.**

`Destroy` 는 씬 4곳에, `DestroyPL` 은 플레이어 프리팹 3개에 붙어 있다. 합치면 **씬과 프리팹을
전부 다시 연결해야 한다.** 상속으로 두면 두 컴포넌트 타입이 그대로 남아 재연결 없이 중복만
사라진다. 42줄 → 25줄.

**동작을 바꾸지 않는 리팩토링에서 "가장 깔끔한 구조"가 항상 정답은 아니다.** 재연결 비용과
그 과정에서 배선을 깨뜨릴 위험이 이득보다 컸다.

## 발견해서 고친 결함 — `BossDie()` 가 매 프레임 돌고 있었다

사망 처리가 `Update()` 안에 조건 없이 들어 있어, **보스가 죽은 뒤에도 매 프레임 계속
실행되고 있었다.** `GetComponent` 를 2회씩 조회하고 `isDash = false` 와 클리어 플래그
설정을 무한히 반복했다.

`defeated` 가드를 둔 `OnBossDefeated()` 로 바꿔 죽는 프레임에 한 번만 돌게 했다.

**여기서 한 프레임이 문제가 됐다.** 사망 블록을 돌진 블록보다 **뒤에** 둬야 한다. 앞에 두면
죽는 프레임의 돌진 이동 1회분이 사라진다. Collider/Rigidbody 비활성화가 이동 뒤로 밀리지만,
이동은 `transform` 직접 대입이고 물리는 `FixedUpdate` 에서 도므로 **프레임 종료 시점의 상태는
같다.** 이 판단 근거를 코드 주석과 커밋 메시지 양쪽에 남겼다.

## 정정한 것 두 건

작업 목록에 올렸다가 **확인해 보니 사실이 아니어서 뺀 것들**이다.

**"`Update()` 안의 `Find` 호출이 20곳"** — 파일 단위 `grep` 으로 센 수였다. `Update()` 안에
있는 것만 세니 **7곳**이었다. 파일에 `Find` 가 있다는 것과 그게 매 프레임 돈다는 것은 다르다.

**"`IsTutorial` 과 `isShake` 가 초기화되지 않는 결함"** — 실제로는 `isShake` 가
`BoolReset.cs:21` 에서, `IsTutorial` 이 `IsTu.Start()` 에서 초기화되고 있었다. 초기화 코드가
다른 파일에 있어서 놓쳤다. **결함이 아니라 내 오독이었다.**

둘 다 지우지 않고 여기 남긴다. 잘못 센 것도 작업 과정의 일부다.
