관련 커밋: `2d103f27` `f5564d71`

관련 항목: [followups 10](../followups.md) (51 → 41개), [followups 14](../followups.md) (새로 염)

## 왜 지금인가 — 하루 만에 싸졌다

08-31 에 구조를 정리하면서 **이름 변경은 미뤄 뒀다.** 그때 `ARCHITECTURE.md` 에 이렇게
적었다.

> 이름은 아직 바꾸지 않았다 — 이름 변경은 직렬화에 영향이 가는지 따로 확인해야 하고,
> 배치 이동과 섞으면 문제가 생겼을 때 어느 쪽 때문인지 가릴 수 없다.

그 사이에 조건 둘이 갖춰졌다.

**1. 회귀를 잡을 수단이 생겼다.** 09-01 에 플레이모드 테스트 7개가 붙었다.

**2. 외부 참조가 0이 됐다.** 어제 `Boss_Spawn` 을 고치면서 구체 타입 4개를 공통 상위
`Monster_Stats` 로 받게 했는데, 그 부수 효과로 `One_Stage_Boss` 와 `Stage_2_monster` 를
**자기 파일 밖에서 부르는 곳이 하나도 남지 않았다.** 바꿀 것이 파일명과 클래스 선언 한
줄씩뿐이었다.

미뤄 둔 것을 다시 볼 조건을 적어 두면 이렇게 값을 한다. 조건이 스스로 갖춰지기도 한다.

## 기준표를 고칠 것인가, 도구를 고칠 것인가

**이번 작업에서 유일하게 판단이 필요했던 지점이다.**

이름을 바꾸자마자 `boss-pattern-diff` 가 깨졌다.

```
FAIL  기준표와 다르다
-One_Stage_Boss
-  scheduler wait 2
-  [0] EarthRock
...
```

기준표(`scripts/baseline/boss-patterns.txt`)가 **클래스 이름으로 항목을 키잉**하는데 그
이름이 사라졌기 때문이다. 두 가지 길이 있었다.

| | 무엇을 하나 | 문제 |
| --- | --- | --- |
| A | 기준표의 이름을 새 이름으로 고친다 | **기준표가 기준이 아니게 된다** |
| B | 도구에 이름 대응표를 넣는다 | 도구가 조금 복잡해진다 |

**B 를 골랐다.** 기준표는 리팩토링 직전(`2f023e52`) 소스의 기록이고, 그 시점에는 저 이름이
맞았다. 지금 이름에 맞춰 기준표를 고치면 "리팩토링 전에는 이랬다"는 증거로서의 성격을
잃는다. 다음에 또 이름을 바꾸면 또 고쳐야 하고, 그러다 보면 기준표가 현재 코드를 따라가는
문서가 되어 버린다 — 그러면 대조할 것이 없다.

그래서 도구에 `CLASS_RENAMED` 를 넣고, **출력할 때 옛 이름으로 되돌린다.** 소스를 찾을
때는 리비전마다 이름이 다르므로 양쪽을 다 시도한다.

```python
CLASS_RENAMED = {"Earth_Boss": "One_Stage_Boss", "Ice_Boss": "Stage_2_monster"}
```

도구에는 이미 코루틴 이름용 `RENAMED = {"BossDash": "Dash", ...}` 가 있었다. 같은 문제를
같은 방식으로 푸는 것이라 새 개념이 늘지 않았다.

**결과가 좋았다.** 같은 도구가 rename 직전 커밋(`2d103f27`)과 작업 트리 양쪽에서 PASS 한다.
즉 **이름 변경을 가로질러 패턴 21개 시퀀스가 같다는 것이 기계로 확인된다.** 기준표를
고쳤다면 이 확인이 아예 불가능했다.

### `2f023e52` 에서 FAIL 나는 것은 정상이다

확인하다 잠깐 놀랐는데, 도구를 `--rev 2f023e52` 로 돌리면 FAIL 이 난다.

```
-  [3] SpawnBullet
+  [3] SpawnTornado
```

**제 수정 탓이 아니다.** D단계에서 고친 결함(followups 7 — 바람 보스 패턴 3이 토네이도를
두 번 부르던 것)이 그 리비전에는 아직 있기 때문이다. 기준표는 그 수정을 반영한 상태다.
수정 전 도구로 돌려 봐서 원래 그랬음을 확인했다.

## 검증을 어떻게 했나

동작이 바뀔 수 없는 작업이지만, **바뀌지 않았다는 것을 어떻게 아는가**가 필요했다.

**바꾸기 전에 세었다.** 18파일 / 41회 (`One_Stage_Boss` 1 · `Stage_2_monster` 1 ·
`Mosnter_Repeat` 2 · `SfxManger` 37). 바꾼 뒤 같은 수가 나왔고 옛 이름은 0회 남았다.
숫자를 먼저 정해 두지 않으면 "다 바꿨다"를 확인할 방법이 없다.

그 밖에 확인한 것.

- **새 이름 4개가 기존에 없는지** — 충돌하면 컴파일 전에 알아야 한다
- **이름이 문자열로 박힌 곳이 있는지** — 씬·프리팹의 `m_Script` 는 전부 GUID 참조였고,
  `GetComponent("이름")` 같은 문자열 호출도 없었다
- **`.cs.meta` 의 GUID 4개가 이동 전후로 같은지** — 이게 다르면 씬 컴포넌트가 전부
  `Missing` 이 된다
- **파일명과 클래스 선언이 일치하는지** — Unity 의 필수 조건이다
- **`.cs` 와 `.cs.meta` 가 전부 짝을 이루는지** — 폴더 전체를 훑었다

`git status` 가 넷 다 `R`(rename)로 잡은 것도 확인했다. 삭제 + 추가로 잡혔다면 `git mv`
가 제대로 안 된 것이다.

## 콘솔에 무해한 예외가 뜬다 — 안 고치고 적어 뒀다

임포트와 테스트는 전부 정상이었는데 콘솔에 이게 남았다.

```
NullReferenceException: Boss_Spawn.Awake () (at .../Boss_Spawn.cs:35)
```

따라가 보니 **결함이 아니라 테스트 구성 때문**이었다. `WindBoss_*` 테스트가 `Mode_Select`
대역을 일부러 안 만들어서 `Mode` 가 null 이다. 널 참조 자체는 2023년 최초 커밋부터 있었고,
실제 플레이에서는 `UI_Select` 를 반드시 거치므로 날 수 없다.

**없애는 방법은 정해져 있고 게임 코드를 안 건드린다.** 다만 확인하려면 Unity 실행을 한 번
더 부탁해야 하고 어차피 테스트를 늘릴 때 같은 자리를 손대므로, **followups 14 로 올리고
미뤘다.** 무해한 예외가 늘 떠 있으면 진짜 문제가 묻히므로 언젠가는 해야 한다.
