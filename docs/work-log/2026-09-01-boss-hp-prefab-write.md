# 2026-09-01 · 체력이 프리팹 에셋에 쓰이던 것을 고쳤다

관련 커밋: `7b55e9be` `f088afe1` `afb62a73` `36020c88` `4f32ce8e` `ab629e4d` `8c2f359d`

관련 항목: [followups 11](../followups.md) (닫음),
[12](../followups.md) · [13](../followups.md) (새로 염)

보스(`Boss_Spawn`)에서 시작해 같은 결함이 몬스터(`Monster_Spawn`)에도 있는 것을 찾아
함께 고쳤다. 오염된 보스 프리팹 값도 되돌렸다.

## 무엇을 했는가

`Boss_Spawn` 이 난이도별 체력을 **인스턴스가 아니라 프리팹 에셋에** 쓰고 있었다.

```csharp
Boss_prefabs[3].GetComponent<Wind_Boss>().Monster_hpMax = Stage_4[0];  // 프리팹 원본
GameObject pre = Instantiate(Boss_prefabs[3], ...);                     // 그 다음에 생성
```

`Boss_prefabs[3]` 은 프리팹 에셋을 가리키는 참조다. 스테이지 1~4 · 이지/하드 8갈래가 전부
같은 형태였다.

전날 플레이모드 테스트를 만들면서 발견했고, **원래 의도를 알 수 없어 고치지 않고
followups 11 로 미뤄 뒀던 것**이다. 이날 그 판단 근거를 찾아서 고쳤다.

## 의도였는지를 추측하지 않고 이력으로 답했다

이게 이 작업에서 제일 중요한 부분이다. 코드만 보면 "일부러 프리팹에 쓴 것인지" 알 수 없다.
그래서 **저장소가 이미 답을 갖고 있는지** 찾아봤다.

먼저 `Boss_Spawn` 프리팹이 들고 있는 난이도 표와 보스 프리팹의 현재 체력을 맞춰 봤다.

| 보스 | 난이도 표 (이지/하드) | 프리팹 현재값 | 어느 쪽인가 |
| --- | --- | --- | --- |
| Rock Creature (대지) | `Stage_1 = [60, 80]` | **80** | 하드 |
| Ice Creature (얼음) | `Stage_2 = [74, 90]` | **74** | 이지 |
| FireBoss (불) | `Stage_3 = [90, 100]` | **90** | 이지 |
| WindBoss (바람) | `Stage_4 = [120, 120]`¹ | **10** | 없음 |

¹ `Boss_Spawn` 프리팹의 `Stage_4` 는 빈 배열이고 `4_StageBoss` 씬이 덮어쓴다.

그다음 그 값들이 언제 그렇게 됐는지 따라갔다.

```
Rock Creature   10 → 30 → 60 → 80   (2023-04-04 ~ 05-04)
Ice Creature    10 → 74             (2023-04-10)
FireBoss        10 → 90             (2023-04-10)
WindBoss        10 (변화 없음)
```

**넷 다 클래스 기본값 `10` 에서 출발해 스포너가 쓰는 값으로 갈아탔다.** 그것도 보스마다
난이도가 제각각이다 — 대지만 하드, 나머지는 이지. 손으로 정한 밸런스 값이라면 `74` 같은
숫자가 나올 리도, 난이도가 뒤섞일 리도 없다.

**결론: 잔재다.** 2023년 팀이 에디터에서 플레이한 흔적이 프리팹에 박혀 그대로 커밋됐다.

### 인코딩을 정규화하고 나서야 보인 것

`Boss_Spawn.cs` 는 CP949 라 주석이 전부 깨져 있었다. UTF-8 로 정규화하니 첫 줄이 이랬다.

```csharp
// 프리팹 스테이지 배치 후 프리팹 언팩 해줘야함. (실수로 프리팹 수치 변경하면 다 변경되서)
```

**작성자는 프리팹 오염이 위험하다는 것을 알고 있었다.** 다만 그것을 코드가 아니라
"배치할 때 언팩해라"라는 수동 규칙으로 막으려 했다. 코드가 프리팹에 체력을 쓰는 것은 그
규칙과 정반대 방향이다.

인코딩 정규화를 "나중에 할 잡일"로 미뤄 두면 이런 것을 못 본다. followups 10 을 파일 단위로
그때그때 처리하는 방식이 여기서 값을 했다.

## 빨강 → 초록을 같은 테스트로 증명했다

**수정하기 전에 테스트를 먼저 쓰고, 수정 전 코드에 대고 돌렸다.**

```
FAIL BossSpawn_WritesHpToTheInstanceNotThePrefabAsset  (2.473s)
     프리팹 에셋의 Monster_hpMax 가 120 로 바뀌었다. 저장소의 WindBoss.prefab 파일이 더러워진다
       Expected: 10
       But was:  120
성공 5  실패 1
```

고친 뒤 같은 테스트가 통과했다.

```
PASS BonginTalk_EnglishLinesGoToEnglishDictionary       (2.733s)
PASS BonginTalk_EnglishLocaleAdvancesAndDoesNotFreeze   (2.516s)
PASS BossSpawn_WritesHpToTheInstanceNotThePrefabAsset   (2.388s)
PASS EarthBullet_ReadsItsOwnDamageNotIceWave            (0.067s)
PASS WindBoss_BulletIsAnIndependentPattern              (2.258s)
PASS WindBoss_BulletPatternFires60Bullets               (5.749s)
성공 6  실패 0  건너뜀 0
```

### 테스트에 값을 박지 않은 이유

`Assert.AreEqual(10, ...)` 로 쓰면 나중에 프리팹 체력을 의도적으로 바꿨을 때 이 테스트가
**엉뚱한 이유로** 실패한다. 대신 이렇게 했다.

1. 난이도를 **둘 다 끈 채로** 씬을 한 번 띄운다 → `Boss_Spawn` 이 아무것도 안 쓴다
2. 그때 프리팹의 원래 값과 씬이 넘기는 스테이지 체력을 읽어 둔다
3. **둘이 다른지 먼저 단언한다** — 같으면 이 테스트가 아무것도 못 잡는다
4. 난이도를 켜고 다시 띄워서, 인스턴스는 스테이지 체력을 받았고 프리팹은 그대로인지 본다

3번이 없으면 테스트가 조용히 무의미해질 수 있다. 통과하는데 아무것도 안 보는 테스트가
제일 나쁘다.

## 내가 틀렸던 것 — 디스크와 메모리를 섞어 적었다

followups 11 에 이렇게 적어 뒀었다.

> **에디터에서 스테이지 4를 플레이하면 프리팹 파일이 바뀐다.**

**틀렸다.** 실제로 관측된 것은 여기까지다.

- 메모리상의 프리팹 에셋이 `10 → 120` 으로 바뀐다 (테스트가 잡았다)
- **디스크의 `WindBoss.prefab` 은 안 바뀐다.** 실패한 실행 직후에도 `git status` 에
  안 나왔고 파일 수정 시각도 그대로였다

디스크에 내려가려면 프로젝트 저장이 한 번 더 있어야 한다. 결함이라는 결론 자체는 그대로다 —
위의 2023년 이력이 **결국 디스크에 도달한다는 것을 이미 증명하고 있다.**

문제는 결론이 아니라 **관측하지 않은 것을 관측한 것처럼 적었다는 것**이다. 전날 나는
`Boss_Spawn` 을 우회해서 테스트를 짰기 때문에 디스크가 더러워지는 것을 **본 적이 없었다.**
프리팹 에셋 변경이 남는다는 일반 지식에서 파일 변경까지 밀어서 써 버렸다.

`followups` 5번에서 "증상을 원인으로 적었다"고 정정한 것과 같은 종류의 실수를, 같은 문서에서
하루 만에 또 했다.

## 과정에서 잘못한 것

**`git stash` 를 썼다.** 경고 수를 수정 전후로 비교하려고 `git stash` → 확인 →
`git stash pop` 을 돌렸다. 결과는 정상이었지만 이 저장소에서는 하면 안 되는 짓이었다 —
Unity 가 늘 건드려 두는 `UserSettings/`, `Packages/` 까지 함께 stash 됐다. 되돌아왔으니
망정이지 중간에 뭐가 어긋났으면 무관한 파일이 날아갔다. 비교는 `git show HEAD:파일` 로
하면 됐다.

**CRLF 파일에 여러 줄짜리 문자열 치환을 또 시도했다.** 파이썬으로 테스트 파일에 코드를
끼워 넣으려는데 두 번째 치환이 안 걸렸다. 파일이 CRLF 인데 치환 문자열이 LF 였다. 이
저장소에서 이 실수가 반복된다 — **디코드한 뒤 `\n` 으로 정규화하고, 쓸 때 `\r\n` 으로
되돌리는 것**을 습관으로 삼아야 한다. 다행히 단언에서 걸려 파일은 안 망가졌다.

## 같은 결함이 Monster_Spawn 에도 있었다

`Monster_Spawn` 이 일반 몬스터 3종에 완전히 같은 짓을 했다. 게다가 `foreach` 안에 있어서
**소환 지점마다 프리팹에 다시 썼다.**

같은 순서로 처리했다 — 인코딩 정규화(`36020c88`) → 6갈래 축약(`4f32ce8e`) →
프리팹 대신 인스턴스(`ab629e4d`). 6갈래 대응도 기계 대조했고 경고가 51 → 45 로
정확히 6개 줄었다(갈래마다 하나씩 있던 미사용 변수).

한 가지는 보스와 다르게 했다. **체력 읽기를 루프 안에 그대로 뒀다.** 밖으로 빼면 소환
지점이 하나도 없을 때 없던 `IndexOutOfRange` 가 생긴다.

### 잔재가 자기를 만든 결함을 가린다

테스트를 쓰다 알게 된 것이고, 이게 이 작업에서 제일 재미있는 부분이다.

**이지 난이도로는 이 결함을 볼 수 없다.** `1_Stage` 의 몬스터 프리팹 값이 `8 / 4 / 6` 인데
그 씬의 이지 체력이 정확히 `8 / 4 / 6` 이다. 프리팹에 쓰든 인스턴스에 쓰든 결과가 같아서
아무것도 드러나지 않는다.

왜 같은가? **그 값들 자체가 에디터에서 이지로 플레이한 잔재이기 때문이다.** 결함이 만든
값이 결함을 보이지 않게 만든다. 하드(`10 / 6 / 8`)로 보면 바로 갈린다.

테스트에 넣어 둔 "전제 확인" 단언이 이걸 잡아 줬다. 처음에 이지로 쓰려다
`Assert.AreNotEqual(pristine, stageHp)` 가 걸릴 것을 계산에서 발견했다. **통과하는데
아무것도 안 보는 테스트**가 될 뻔했다.

## 테스트 하나가 다른 테스트 둘을 죽였다

`1_Stage` 를 띄우는 테스트를 넣자 관계없어 보이는 `WindBoss` 테스트 2개가 죽었다.

```
FAIL WindBoss_BulletIsAnIndependentPattern  (0.054s)
     Unhandled log message: '[Exception] NullReferenceException'
     InventoryUI.RedrawSlotUI () (at Assets/Scripts/Item/InventoryUI.cs:42)
```

**전에 `Camera_test` 로 겪은 것과 같은 형태다.** 매 프레임 예외를 던지는 것이 남아 있으면
그 로그가 **다음 테스트에 귀속되어** 그쪽을 실패시킨다. 실패 시간이 0.05초인 것이 단서다 —
테스트 본문이 시작되기도 전에 죽었다는 뜻이다.

원인은 또 **스테이지 씬이 단독으로 서지 못한다**는 것이었고, 이번엔 전제가 둘 더 나왔다.

**1. `Inventory.instance` 가 없다.** `InventoryUI.Start` 가 이렇게 되어 있다.

```csharp
if (Inventory.instance != null) { inven = Inventory.instance; }
else { Inventory.instance = inven; }        // inven 은 아직 null 이다
```

`else` 가 하필 **null 을 대입한다.** 그래서 `inven` 이 끝까지 null 이고 `Update` 가 매
프레임 터진다. 실제 게임에서는 플레이어 프리팹이 `Inventory` 를 들고 다녀서 안 걸린다.

**2. `Far_Attack_Pos` 태그가 없다.** `Far_Monster.Start` 가 널 검사 없이
`FindGameObjectWithTag("Far_Attack_Pos").transform` 을 부른다. 대역에 그 태그가 없었다.

### 하나씩 겪지 않으려고 태그를 전부 뽑았다

두 번 물리고 나서, 남은 것을 마저 맞기 전에 **스크립트가 `FindWithTag` 로 찾는 태그를 전부
뽑아** 실제 플레이어 프리팹(`Player_Sword` 등)이 다는 태그와 대조했다.

```
플레이어 프리팹이 다는 태그: Far_Attack_Pos, Monster_Skill_Pos, Player, Player_Hit, Player_Weapon
대역이 갖고 있던 것:         Player, Player_Hit
```

셋이 빠져 있었다. 한 번에 채우고 나니 7개가 전부 통과했다. **한 번 물릴 때마다 사용자에게
Test Runner 실행을 부탁해야 하는 환경이라, 남은 것을 미리 세는 쪽이 싸다.**

## 프리팹 값을 되돌렸다 — 보스만

`8c2f359d` 에서 보스 프리팹 3개의 잔재를 클래스 기본값 `10` 으로 되돌렸다. 넷 다 `10` 에서
출발했고 오염되지 않은 `WindBoss` 가 아직 `10` 이라 기준이 있었다.

**몬스터 프리팹 9개는 되돌리지 않았다.** 6개가 마지막 변경에서 정확히 이지 값으로 갈아탄
것까지는 같은데, 이력에 손으로 만진 값이 섞여 있어(`Rock_1` 의 `1000` 같은) **되돌릴 목표를
정할 근거가 없다.** 마지막 변경이 오염이었는지 이지 값에 맞춘 의도적 조정이었는지 구분되지
않고, 숫자가 한 자리라 우연히 겹칠 여지도 보스보다 크다. followups 13 으로 올렸다.

**되돌린다고 결함의 증거가 사라지지는 않는다.** 값과 이력은 git 과 이 문서에 남아 있다.

## 검증하지 못한 것

- **스테이지 1~3 과 하드 난이도.** 테스트는 `4_StageBoss` 의 이지 한 갈래만 실제로 돌린다.
  코드 경로는 하나로 합쳐졌고 8갈래 대응을 기계 대조했지만, **실행해 본 것은 한 갈래다.**
- **디스크 기록 여부.** 프로젝트를 저장하면 프리팹 파일이 실제로 바뀌는지 직접 확인하지
  않았다. 확인하려면 일부러 저장하고 되돌려야 해서 하지 않았다. 2023년 이력이 간접
  증거다.
- **`Monster_Spawn` 은 손대지 않았다.** 일반 몬스터 3종에 완전히 같은 패턴이 있다
  (`Monster_prefabs[0].GetComponent<Normal_Monster>().Monster_hpMax = ...`). 이번 범위에
  넣을지 정하지 않아 그대로 뒀다.
- **이미 오염된 프리팹 값(80/74/90)을 되돌리지 않았다.** 스포너가 항상 덮어쓰므로 게임에는
  영향이 없지만, 저장소는 "의미 있어 보이는데 사실 잔재인 값"을 계속 들고 간다.
- **2·4스테이지와 이지 난이도의 몬스터 소환.** `Monster_Spawn` 테스트는 `1_Stage` 하드 한
  갈래만 실제로 돌린다. 6갈래 대응은 기계 대조했다.
- **되돌린 보스 프리팹 3개를 에디터에서 눈으로 확인하지 않았다.** Unity 가 켜진 상태로
  디스크를 고쳤으므로 재임포트 후 값이 정상인지 봐야 한다.
