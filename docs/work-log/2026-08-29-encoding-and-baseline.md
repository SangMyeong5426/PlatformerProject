# 2026-08-29 · 리팩토링 준비: 인코딩 정규화와 동작 기준표

> **소급 작성 (2026-08-31).** 작업 당시에는 work log 폴더가 없었다.
> 커밋 메시지와 작업 세션 기록을 근거로 다시 썼다.

관련 커밋: `e5d9e6bb` (2026-08-27), `2f023e52`

## 무엇을 했는가

보스 4종을 공통 골격으로 묶기 전에 두 가지를 먼저 했다.

**하나. 파일 인코딩을 CP949 에서 UTF-8(BOM) 로 정규화했다.** 2023년 팀 작업 당시 Visual
Studio 기본값으로 저장된 파일들이라 한글 주석이 CP949 로 들어 있었다. 이 상태로 편집하면
주석이 깨지고, 무엇보다 **diff 가 판독 불가능해서 리팩토링 결과를 검토할 수 없다.**

**둘. 동작 기준표를 만들었다.** 보스 4종의 패턴 실행 시퀀스 — 대기 시간, `anim` 파라미터,
SFX 키, 생성·파괴 순서 — 를 리팩토링 전 소스에서 뽑아 표로 만들었다.

## 왜 기준표를 먼저 만들었는가

**이 저장소에는 테스트가 하나도 없다.** 동작을 바꾸지 않는 리팩토링인데 "바뀌지 않았다"를
증명할 수단이 없었다.

"컴파일이 된다"는 검증이 아니다. 보스 패턴은 코루틴 안에서 `yield return new
WaitForSeconds(1f)` 가 줄줄이 이어진 구조라, 대기 하나를 빠뜨리거나 순서를 바꿔도 컴파일은
멀쩡히 된다. 플레이해서 눈으로 보는 것도 패턴이 랜덤으로 골라져 재현이 안 된다.

그래서 **무엇이 같아야 하는지를 코드를 건드리기 전에 먼저 고정했다.** 이후 모든 리팩토링
커밋은 이 표와 대조해서 "20/20 일치"를 확인하고 올렸다.

## 인코딩 정규화를 별도 커밋으로 분리한 이유

BOM 추가와 한글 주석 재인코딩은 **파일의 거의 모든 줄을 바꾼다.** 내용 변경과 같은 커밋에
넣으면 실제로 무엇을 고쳤는지 diff 에서 영영 볼 수 없다.

그래서 이후에도 원칙을 유지했다 — **편집 대상이 되는 파일만 그때그때 정규화하고, 정규화는
항상 직전 커밋으로 분리한다.** 저장소 전체를 한 번에 변환하지 않았다. 한꺼번에 하면 거대한
diff 하나가 생기고 그 안에 실수가 섞여도 알 수 없다.

검증은 **변환 전후 텍스트가 문자 단위로 동일한지**를 스크립트로 비교했다. CP949 로 디코딩한
결과와 UTF-8 로 다시 읽은 결과가 같아야 한다. CRLF 보존과 단독 LF 0개도 함께 확인했다.

## 남은 문제

**기준표와 대조 스크립트가 저장소에 없다.** 세션 스크래치패드에서 만들어 썼고 세션이 끝나며
사라졌다. 지금 다시 대조하려면 처음부터 만들어야 한다.

이 프로젝트에서 가장 설명할 만한 부분이 **"테스트가 없는 저장소에서 동작 동일성을 어떻게
검증했는가"** 인데, 정작 그 수단이 저장소에 한 줄도 남아 있지 않다.
