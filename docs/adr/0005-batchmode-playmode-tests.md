# ADR 0005: 런타임 검증을 배치모드 플레이모드 테스트로 한다

- 상태: Accepted
- 날짜: 2026-09-01
- 소급 작성: **아니오.** 구현 전에 작성했다

## 배경

리팩토링 A~D단계가 끝났는데 **런타임 검증이 하나도 안 됐다.** [`followups`](../followups.md)
의 열린 항목 대부분이 "게임을 조작할 수 있을 때"로 미뤄져 있다.

지금 가진 검증 수단은 둘 다 정적이다.

| 도구 | 무엇을 보는가 | 무엇을 못 보는가 |
| --- | --- | --- |
| `scripts/compile-check` | 컴파일이 되는가 | 실행하면 어떻게 되는가 |
| `scripts/boss-pattern-diff` | 패턴 연산 시퀀스가 같은가 | 그 시퀀스가 실제로 도는가 |

**둘 다 소스를 읽을 뿐 실행하지 않는다.** C단계에서 고친 영어 로케일 멈춤 결함이 정확히 이
빈틈에서 나왔다 — 컴파일도 되고 패턴도 안 건드렸지만 실행하면 `Awake` 에서 예외가 났다.

손으로 플레이하는 것에도 한계가 있다.

- **재현이 안 된다.** 다음에 같은 것을 다시 확인하려면 같은 조작을 처음부터 반복해야 한다
- **회귀를 못 잡는다.** 오늘 확인한 것이 내일 깨져도 모른다
- **대지 탄환은 손으로도 확인이 안 된다.** 두 데미지 값이 모두 `1` 이라 어느 쪽을 읽든
  화면에 같은 결과가 나온다

## 검토한 선택지

**A. Unity Test Framework 플레이모드 테스트를 배치모드로 돌린다**

`playModeTestRunnerEnabled` 를 켜면 테스트가 `Assembly-CSharp` 안에 들어가 게임 코드를
그대로 볼 수 있다. CLI 로 창 없이 실행한다.

```
Unity.exe -batchmode -projectPath . -runTests -testPlatform PlayMode -testResults results.xml
```

- 장점: **게임 루프가 실제로 돈다.** 코루틴, `WaitForSeconds`, 씬 로드가 진짜로 동작한다
- 장점: **실제 씬을 그대로 쓴다.** 14개 씬이 전부 빌드 설정에 있어 `SceneManager.LoadScene`
  으로 로드된다. 씬 배선(프리팹 참조, 인스펙터 값)까지 검증 범위에 들어온다
- 장점: 창이 없으므로 `runInBackground` 와 무관하다
- 단점: **Unity 를 닫아야 한다.** 배치모드가 프로젝트를 독점한다
- 단점: 테스트가 `Assembly-CSharp` 에 섞인다. `UNITY_INCLUDE_TESTS` 로 빌드에서는 빠지지만
  소스 트리에는 함께 있다

**B. 게임 코드에 `asmdef` 를 만들고 테스트 어셈블리를 분리한다**

- 장점: 테스트가 게임 코드와 어셈블리 단위로 분리된다. 보통 이 방식을 권장한다
- 단점: **`asmdef` 어셈블리는 `Assembly-CSharp` 을 참조할 수 없다.** 그래서 게임 코드 전체를
  `asmdef` 로 옮겨야 하는데, `Assets/Scripts/` 밖에 `.cs` 가 99개 더 있다. 이들과의 참조
  방향을 전부 확인해야 한다
- 단점: **컴파일 단위를 바꾸는 변경이다.** 지금 하려는 건 검증을 붙이는 것인데, 검증을 붙이려고
  빌드 구조를 먼저 바꾸면 **무엇이 깨졌을 때 원인이 둘이 된다**

**C. 에디터 스크립트를 `-executeMethod` 로 돌린다**

`Assets/Editor/` 는 `Assembly-CSharp-Editor` 로 컴파일되고 이쪽은 `Assembly-CSharp` 을
참조할 수 있다. 설정 변경이 전혀 필요 없다.

- 장점: 프로젝트 설정을 하나도 안 건드린다
- 단점: **에디트 모드다. 게임 루프가 없다.** 코루틴을 `MoveNext()` 로 직접 돌려야 하고
  `WaitForSeconds` 는 흉내를 내야 한다. **그건 실행이 아니라 시뮬레이션**이고, 지금
  `boss-pattern-diff` 가 하는 일과 본질적으로 같다
- 단점: 결과 리포트 형식을 직접 만들어야 한다

**D. 손 플레이만 하고 결과를 work log 에 적는다**

- 장점: 비용 0
- 단점: 재현·회귀·대지 탄환 문제가 그대로 남는다. **지금 상태다**

## 결정

**A — 배치모드 플레이모드 테스트.**

핵심 근거는 **C가 못 하는 것을 A가 한다**는 것이다. 이 저장소에 이미 정적 검증 도구가 둘 있고
그것들로 잡히지 않은 결함이 실제로 나왔다. 필요한 건 "소스를 더 잘 읽는 도구"가 아니라
**실행**이다. C는 정적 도구를 하나 더 만드는 것에 가깝다.

B를 고르지 않은 이유는 **순서**다. B가 최종적으로 더 나은 구조인 것은 맞다. 그러나 지금
어셈블리를 쪼개면 그 작업 자체가 검증이 필요한 큰 변경이 되고, 정작 검증 수단은 아직 없다.
**검증 수단을 먼저 세우고, 그 다음에 어셈블리를 쪼개면 쪼개는 작업을 테스트로 지킬 수 있다.**

"Unity 를 닫아야 한다"는 단점은 감수한다. 이 저장소는 이미 파일 이동 때 에디터를 닫는 절차를
쓰고 있고, 1인 작업이라 조율 비용이 없다.

**실제 씬을 로드해서 검증한다.** 테스트용 씬을 따로 만들지 않는다. 만들면 그 씬의 배선이
실제 씬과 같다는 것을 또 검증해야 하고, 리팩토링에서 깨지기 쉬운 것이 바로 **씬 배선**이다.
`4_StageBoss` 를 그대로 띄워서 확인해야 그 씬이 실제로 돈다는 것이 확인된다.

## 함께 바꾸는 것 — `runInBackground`

`ProjectSettings.asset` 의 `runInBackground` 를 `0` 에서 `1` 로 바꾼다.

이 값이 `0` 이어서 **창이 비활성이면 게임 루프가 멈춘다.** [`CLAUDE.md`](../../CLAUDE.md) 와
followups 5번에 "Unity 창이 비활성이면 플레이 모드가 진행되지 않는다"고 적어 둔 현상의
정체가 이 설정이다. 원인을 모른 채 증상만 적어 뒀던 것이다.

**배치모드 테스트는 창이 없어서 이 설정과 무관하다.** 그래도 바꾸는 이유는 손으로 확인할 때
필요하기 때문이다. 값을 세거나 로그를 보려고 다른 창을 보는 순간 게임이 멈춘다.

**이건 동작 변경이다.** 빌드된 게임도 알트탭 후 계속 돌게 된다. 리팩토링 범위 밖이므로
사용자에게 확인받고 바꿨고, **별도 커밋으로 분리**한다.

## 영향

**쉬워지는 것**

- followups 2·3·4·5 가 자동 검증 대상이 된다
- 대지 탄환처럼 **손으로는 확인 불가능한 것**이 확인 가능해진다. 테스트에서 두 데미지 값을
  다르게 넣으면 어느 쪽을 읽는지 드러난다
- 앞으로의 리팩토링이 회귀 안전망을 갖는다

**비용 · 위험**

- **Unity 를 닫아야 실행된다.** 자동으로 돌 수 없고, 잊으면 검증 없이 커밋하게 된다
- `scripts/compile-check` 에 nunit 참조를 추가해야 한다. 안 하면 테스트 파일에서 실패한다
- 테스트가 실제 씬을 로드하므로 **씬이 바뀌면 테스트도 손봐야 한다.** 대신 씬 배선을 검증
  범위에 넣는 대가다
- **키 입력은 검증할 수 없다.** `activeInputHandler: 0` (구 Input Manager)이라
  `Input.GetKeyDown` 을 코드로 만들어낼 방법이 없다. 대화 진행은 키 입력이 호출하는
  코루틴을 리플렉션으로 직접 불러 그 아래를 검증한다. **키를 읽는 한 줄은 미검증으로
  남고, 그 사실을 테스트 주석과 work log 에 적는다**

## 다시 볼 조건

- **배치모드가 이 프로젝트에서 실제로 돌지 않으면** 즉시 다시 본다. Localization 초기화가
  배치모드에서 막히는 사례가 알려져 있다. 그 경우 C로 후퇴하고 그 사실을 남긴다
- **테스트가 20개를 넘으면** B(어셈블리 분리)를 다시 본다. 그 시점엔 테스트 코드가
  게임 코드에 섞여 있는 것이 실제로 방해가 된다
- **입력 시스템을 새 Input System 으로 옮기게 되면** 다시 본다. 그때는 키 입력까지
  검증 범위에 들어온다
