# ADR 0002: 보스 공통화를 상속 계층이 아니라 `virtual` 훅으로 한다

- 상태: Accepted
- 날짜: 2026-08-31
- 소급 작성: **예.** 실제 적용은 2026-08-30 (`03495f2f`..`626a80f0`)

## 배경

불·바람·대지·얼음 보스 4종이 **패턴 스케줄러와 돌진·텔레포트 코루틴을 각자 복붙해서** 갖고
있었다. 구조는 같고 값만 달랐다.

| 다른 것 | 어떻게 다른가 |
| --- | --- |
| 돌진 애니메이션 파라미터 | 불·바람 `"Dash"` / 대지·얼음 `"Run"` |
| 텔레포트 선딜 | 0.5초 / 얼음만 0.8초 |
| 텔레포트 후딜 | 0.8초 / 바람 1.0초 / 대지 1.5초 |
| 돌진 효과음 | 대지만 `"Rock_Rush"` |
| 패턴 목록 | 보스마다 다르고 개수도 다르다 |
| 클리어 플래그 | 스테이지가 다르다. 모드 보스는 없다 |

`Basic_Boss` 라는 공통 부모는 이미 있었지만 **체력·데미지 필드만 갖고 있었고** 행동은
전부 자식이 복붙하고 있었다.

## 검토한 선택지

**A. `virtual` 훅으로 값과 동작을 재정의한다 (Template Method)**

`Basic_Boss` 가 스케줄러와 공통 코루틴을 갖고, 보스별 차이는 `protected virtual` 프로퍼티와
메서드로 뺀다.

- 장점: **차이가 나는 지점이 훅 목록으로 한눈에 보인다.** "이 보스는 무엇이 다른가"가
  오버라이드 목록과 같다
- 장점: 기존 클래스 구조가 그대로라 **씬·프리팹 재연결이 필요 없다**
- 단점: 훅이 늘어나면 부모가 비대해진다

**B. 설정 데이터를 `ScriptableObject` 로 빼고 보스 클래스는 하나만 둔다**

- 장점: 값 조정이 코드 변경 없이 된다. 기획자가 만질 수 있다
- 단점: **씬·프리팹의 컴포넌트를 전부 갈아 끼워야 한다.** 클래스 4개가 1개가 되므로
  ADR-0001 의 이관 작업이 전 보스에 대해 필요하다
- 단점: 패턴 코루틴은 데이터로 뺄 수 없다. 결국 클래스는 남고 데이터만 분리된다
- 단점: **동작을 바꾸지 않는 리팩토링의 범위를 넘어선다.** 이건 설계 변경이다

**C. 패턴을 클래스로 빼고 조합한다 (Strategy)**

- 장점: 패턴 재사용과 조합이 자유롭다
- 단점: 클래스가 패턴 수만큼 늘어난다. 지금 패턴은 보스당 3~4개고 보스 간 공유되는 것은
  돌진·텔레포트 둘뿐이다. **얻는 것에 비해 파일이 너무 늘어난다**
- 단점: B와 같은 이유로 범위를 넘어선다

## 결정

**A — `protected virtual` 훅.**

핵심 근거는 **이 작업이 동작을 바꾸지 않는 리팩토링**이라는 것이다. B와 C는 더 나은 설계일
수 있으나 씬·프리팹 재연결을 동반하고, 그 과정에서 배선이 깨지면 **무엇 때문에 깨졌는지
추적할 수 없다** — 구조 변경과 동작 변경이 한 커밋에 섞이기 때문이다.

A는 클래스 구조를 그대로 두므로 씬을 한 줄도 건드리지 않는다. 검증이 **소스 대조만으로**
끝난다.

또 하나. **훅 목록 자체가 문서 역할을 한다.** 4종의 차이가 흩어져 있어서 "대지 보스만
효과음이 있다"는 걸 알려면 네 파일을 다 읽어야 했다. 지금은 `Earth_Boss` 의 오버라이드
목록이 그 답이다.

**패턴 목록은 `System.Func<IEnumerator>[]` 로 받는다.** 스케줄러가 인덱스로 고르고
`StartCoroutine` 으로 실행한다. 각 패턴이 끝에서 다음 패턴을 재귀 호출하던 구조를
`while` 루프로 바꿔, **패턴은 자기 동작만 하고 다음을 고르는 일은 스케줄러가** 하도록 분리했다.

## 영향

**쉬워지는 것**

- 보스를 추가하려면 `BuildPatterns()` 와 다른 훅만 재정의하면 된다
- 스케줄러를 고치면 4종에 동시에 적용된다. 실제로 바람 보스의 `base.Update()` 누락 결함이
  통합 과정에서 드러나 해소됐다

**비용 · 위험**

- **부모가 자식의 사정을 알게 된다.** `DashAnimParam` 같은 훅은 특정 자식 때문에 존재한다.
  훅이 계속 늘면 부모가 "모든 보스의 차이점 목록"이 되어 다시 읽기 어려워진다
- 검증용 필드(`debugForcePattern`)가 프로덕션 코드에 남았다. 패턴이 랜덤으로 골라져 이게
  없으면 런타임 검증이 불가능했다. `[Header("디버그")]` 로 용도를 명시하는 것으로 타협했다

## 다시 볼 조건

- **훅이 10개를 넘으면** 다시 본다. 그 시점엔 B(설정 데이터 분리)의 비용이 정당화된다
- **보스를 새로 추가하게 되면** 다시 본다. 지금 구조는 기존 4종을 설명하기 위해 만들어졌고,
  새 보스가 훅으로 표현되지 않는 차이를 가지면 그때가 신호다
