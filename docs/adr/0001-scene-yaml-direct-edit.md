# ADR 0001: 씬 컴포넌트 교체를 에디터 대신 씬 YAML 직접 편집으로 한다

- 상태: Accepted
- 날짜: 2026-08-31
- 소급 작성: **예.** 실제 적용은 2026-08-30 (`4391e103`, `1e427036`, `0c951b69`)

## 배경

거의 같은 컴포넌트 클래스 여러 개를 하나로 합치면, **이미 씬과 프리팹에 붙어 있는 인스턴스를
새 클래스로 갈아 끼워야 한다.** B단계에서 인스턴스 9개(보스 포탈 5, 대화 트리거 4)가 대상이
됐다.

제약이 둘 있었다.

- **동작을 바꾸지 않는 리팩토링이다.** 무엇이 바뀌었고 무엇이 안 바뀌었는지 증명할 수 있어야
  한다. 증명 수단은 `git diff` 뿐이다 — 이 저장소에는 테스트가 없다
- **인스펙터에 입력된 값을 잃으면 안 된다.** 포탈 참조, 대화 패널 참조, 진행도 임계값이
  씬마다 다르게 들어 있다

## 검토한 선택지

**A. 에디터에서 컴포넌트를 바꿔 단다 (정상적인 방법)**

씬을 열고 기존 컴포넌트를 제거한 뒤 새 것을 붙이고 인스펙터 값을 다시 입력한다.

- 장점: Unity 가 보장하는 방식이다. 직렬화 형식을 몰라도 된다
- 단점: **씬을 저장하면 씬 전체가 재직렬화되어 수백 줄이 바뀐다.** 내가 의도한 변경과
  Unity 가 자동으로 건드린 변경이 diff 에서 구분되지 않는다
- 단점: 값을 손으로 다시 입력하므로 **오타가 나도 컴파일에 걸리지 않는다.** 인스턴스 9개를
  눈으로 대조하는 수밖에 없다

**B. 씬 YAML 을 직접 편집한다**

`m_Script` 의 GUID 를 새 클래스 것으로 바꾸고 필드 줄을 고친다.

- 장점: **인스턴스당 3~4줄만 바뀐다.** 9개 전부를 `git diff` 로 검토할 수 있다
- 장점: 구 클래스의 GUID 가 저장소 전체에서 0건인지 **기계적으로 셀 수 있다**
- 단점: Unity 직렬화 형식을 알아야 한다. `stripped` Transform, `PrefabInstance` 의
  `m_Modifications` 처럼 형태가 다른 경우를 잘못 건드리면 씬이 깨진다
- 단점: Unity 가 보장하지 않는 방법이다

**C. 에디터 스크립트를 써서 일괄 교체한다**

- 장점: 반복 작업을 자동화한다
- 단점: **저장 시 재직렬화는 A와 똑같이 일어난다.** diff 문제가 해결되지 않는다
- 단점: 이 작업만을 위해 에디터 스크립트를 만드는 비용이 인스턴스 9개보다 크다

## 결정

**B — 씬 YAML 직접 편집.**

결정적인 이유는 **diff 로 검증할 수 있는가**였다. A와 C는 씬 저장 시 재직렬화가 일어나
"의도한 변경만 했다"를 증명할 수 없다. 동작을 바꾸지 않는 리팩토링에서 그 증명을 포기하면
작업의 근거가 통째로 없어진다.

A를 고르지 않은 두 번째 이유는 **검증 방법이 눈으로 보는 것뿐**이라는 점이다. B를 고르면
GUID 개수 세기라는 기계적 검증이 따라온다 — 구 GUID 4개가 씬·프리팹 전체에서 0건이고 새
GUID 가 예상한 수만큼 나오면 빠뜨린 인스턴스가 없다는 뜻이다.

## 영향

**쉬워지는 것**

- 컴포넌트 이관을 커밋 단위로 검토할 수 있다
- 잔여 참조 0건을 증명할 수 있다
- 모달 저장 대화상자 없이 작업이 진행된다

**어려워지는 것 · 위험**

- Unity 직렬화 형식을 알아야 한다. 실제로 `PrefabInstance` 안의 컴포넌트는 씬에 직접 붙은
  것과 형태가 달라 별도로 다뤄야 했다
- **직접 편집한 뒤 반드시 에디터에서 씬을 열어 인스펙터를 확인해야 한다.** YAML 이 문법적으로
  맞아도 Unity 가 다르게 해석할 수 있다. 실제로 B단계에서 5개 씬을 열어 인스턴스 9개를
  전부 확인했다
- **에디터가 켜져 있으면 미저장 상태가 씬 전환 시 디스크에 써진다.** 실제로 `Player.unity`
  가 의도치 않게 변경돼 되돌린 일이 있다
  ([work log](../work-log/2026-08-30-component-consolidation.md))

## 다시 볼 조건

이관 대상 인스턴스가 **수십 개 규모**가 되면 다시 본다. 손으로 YAML 을 고치는 비용이
에디터 스크립트를 만드는 비용을 넘어선다. 그때는 C 를 쓰되 diff 검증을 어떻게 대신할지
함께 정해야 한다.
